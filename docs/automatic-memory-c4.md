# Automatic Memory C.4 — Consentimiento persistente y cola local experimental

## Estado y alcance

C.4 implementa registros locales y controles de sesión, pero no conecta Automatic Memory al agente de la CLI para extraer candidatos. No hay extractor real inyectado, llamadas adicionales a OpenAI, escritura de recuerdos ni activación de Memory2. El detector solo puede ejecutarse si un host de código lo habilita expresamente, inyecta un detector y existe consentimiento persistente vigente. El consentimiento por sí solo nunca activa el extractor. `automaticSavingEnabled` permanece en `false`.

C.3 documenta el comportamiento original de consentimiento volátil. Este documento describe el estado de C.4 y lo sustituye para persistencia y cola.

## Consentimiento persistente

Los comandos `/automatic-memory consent` y `/automatic-memory confirm-consent <desafío>` implementan un intercambio de dos turnos leídos directamente desde `stdin`. La solicitud presenta propósito, alcance, categorías contempladas, exclusiones, persistencia local y la separación entre análisis y guardado. El siguiente turno debe contener exactamente el desafío aleatorio. El desafío solo vive en memoria, se consume con la siguiente entrada y no se serializa. Respuestas del modelo, argumentos de tools, memoria recuperada y texto citado no pueden confirmar.

La aceptación guarda un registro pequeño con versión de política, propósito, alcance, fecha, estado, un ID opaco aleatorio y una lista acotada de IDs aleatorios de conversaciones excluidas. No guarda texto, categorías mencionadas en una conversación, desafío ni secreto reutilizable. Su alcance son únicamente turnos directos futuros en ejecuciones posteriores; nunca historial anterior. El registro declara `grantsMemoryWrite: false`. El cambio de versión de política se rechaza cerradamente hasta obtener una nueva aceptación; no se reescribe consentimiento viejo como si aceptara la política nueva.

El archivo vive en `%LOCALAPPDATA%\Nexa\AutomaticMemory\consent.json` en Windows y en `${XDG_DATA_HOME:-~/.local/share}/nexa/automatic-memory/consent.json` en Unix. Solo se crea al aceptar o revocar. Las escrituras usan archivo temporal exclusivo, sincronización del archivo y rename bajo un lock cooperativo. Un archivo corrupto, un lock persistente o un error de escritura no habilitan análisis; no se limpia un lock que podría pertenecer a otro proceso. La revocación escribe un tombstone `revoked` y, por separado, intenta invalidar propuestas pendientes/aprobadas enlazadas al ID de consentimiento. Un fallo al limpiar la cola no impide escribir la revocación; sin consentimiento vigente esas propuestas quedan ocultas y no pueden aprobarse. Cada instancia vuelve a leer el consentimiento en cada turno directo y antes de la fase de evaluación para observar una revocación local desde otra CLI. Una solicitud externa que ya haya comenzado no se puede retirar retroactivamente; no hay extractor real conectado en C.4. Si no puede guardarse la revocación, la sesión actual se desactiva y el CLI informa que la revocación persistente no pudo confirmarse.

Esto no constituye autenticación humana ni protección contra otro proceso del mismo usuario que pueda editar archivos locales. En Unix el directorio se limita a modo 0700 y archivos a 0600; en Windows se heredan ACL de `LOCALAPPDATA`, que Node no verifica ni endurece. No hay firma o MAC y no deben añadirse secretos de autorización al archivo. Consentir análisis persistente no configura detector, red, costos ni guardado.

## Conversación CLI y exclusión puntual

En la CLI actual, una “conversación” de Automatic Memory es la instancia de `createAgent()` iniciada por una ejecución del proceso. El runtime genera un `sessionId` aleatorio al crear el agente; no se trata como identidad humana ni se reutiliza entre procesos. La frase exacta `Nexa, no recuerdes esta conversación` y el comando `/automatic-memory exclude-conversation` se reconocen únicamente en la entrada directa de stdin, antes de enviar texto al modelo.

La frase `Nexa, no aprendas de este mensaje:` al inicio de un turno marca solo ese turno como excluido. El mensaje puede seguir llegando al modelo conversacional para responder, pero el preflight de Automatic Memory lo descarta antes del extractor; los turnos posteriores no se excluyen. La frase aislada también se descarta. Esto se reconoce sobre texto directo de stdin y es una instrucción de privacidad, no un permiso. La decisión de permitir este control por mensaje queda implementada; todavía no hay extractor conectado que pueda analizar el resto de los turnos.

La exclusión de conversación detiene evaluaciones de turnos siguientes de esa instancia, aborta cooperativamente la evaluación en vuelo, invalida la confirmación de cola en memoria y elimina propuestas pendientes/aprobadas vinculadas a esa conversación. El consentimiento conserva su lista de exclusiones mientras siga vigente; la cola también conserva un tombstone mínimo por 30 días para rechazar propuestas tardías con el mismo ID. Si falla la limpieza de la cola, la exclusión persistida se usa para ocultar y bloquear esas propuestas. Si falla persistir la exclusión, la ejecución actual sigue excluida y el CLI avisa que el estado entre sesiones no pudo confirmarse. La exclusión no elimina recuerdos históricos, no revoca el consentimiento de otras conversaciones y no altera Memory1. Otra ejecución CLI es otra conversación; el actual repo no dispone de identidad confiable para conversaciones remotas o canales futuros.

## Cola local de propuestas

La cola C.4 es una infraestructura experimental consumible por código confiable; el detector de C.2/C.3 no la alimenta. No hay un camino desde el modelo o tools hasta `enqueue`. El contrato cerrado solo admite `ADD`/`REPLACE`, una categoría permitida, un resumen de hasta 180 caracteres y, para REPLACE, un resumen de destino. No acepta texto original, historial, IDs canónicos, assertion, provenance, grant, capability ni recibo. Screening de secretos, patrones de identificadores y caracteres de control de terminal falla cerrado. Datos de pacientes, secretos profesionales y texto de cita/importación se rechazan. El screening es heurístico; un llamador de código confiable aún debe construir resúmenes mínimos y no identificables. Las entidades personales de terceros no tienen categoría de cola en esta versión.

La cola se almacena en `proposals.json` junto al registro de consentimiento. Cada propuesta lleva ID aleatorio opaco, conversación, consentimiento, turno aleatorio, fingerprint SHA-256 de campos estructurados, categoría, acción, sensibilidad, resumen, fecha y expiración. No almacena el texto fuente. La huella se usa para deduplicar la misma propuesta en una conversación; no es autenticación ni autorización. Repeticiones pendientes o ya aprobadas durante su retención devuelven el ID existente.

El vencimiento es siete días desde creación y se comprueba en cada lectura o mutación: una propuesta pendiente expirada pasa a `expired` y sus resúmenes se borran. El validador además exige que `expiresAt` coincida con `createdAt + 7 días`, así una fecha manipulada no extiende la retención. La revisión agrupada muestra categoría/acción y resúmenes, pero cada elemento requiere revisión individual. `/automatic-memory review <id>` muestra el plan limitado y emite un desafío efímero de 60 segundos; la siguiente entrada directa debe confirmar el ID y desafío exactos. Esta acción solo marca el objeto de cola como `approved`; no genera capability ni autoriza persistencia. `reject-proposal` elimina de inmediato resumen/target y conserva tombstone; `discard-proposal` elimina el elemento completamente. El contenido aprobado se conserva hasta su expiración de siete días y luego se borra; los estados terminales sin contenido se purgan después de 30 días.

La cola no ofrece método de escritura a MemoryService, repositorio ni ejecutor. No existe mecanismo de ejecución desde “approved”. Una futura fase necesitará convertir una aprobación en operación canónica y pasar por un coordinador y escritor revisados; no debe interpretar el estado `approved`, el fingerprint, un booleano ni `auto_save` como autoridad.

## Protección y recuperación locales

Ambos archivos son JSON versionados y con esquema cerrado. Lectura no crea ni corrige archivos. Corrupción, exceso de tamaño, symlinks en el archivo final, rutas inválidas y errores de validación se reportan con códigos fijos y no se sobrescriben automáticamente. La actualización toma un lock `wx`, escribe un temporal exclusivo, lo sincroniza y lo publica mediante rename. Las pruebas cubren dos procesos Node cooperativos escribiendo sobre el mismo archivo temporal; no prueban bloqueo frente a escritores externos que ignoren el lock. Los locks no se roban ni expiran automáticamente; tras una caída puede requerirse inspección local y eliminación manual únicamente cuando se confirme que el proceso dueño terminó. El rename y `sync()` de archivo no prueban durabilidad ante pérdida de energía, almacenamiento defectuoso, todos los filesystems o reemplazo atómico universal. No hay cifrado adicional; los ACL de usuario y la reducción del contenido son la protección local disponible.

## Autonomía selectiva futura

La política de producto indicada distingue recuerdos estables/de bajo riesgo, candidatos sensibles que requieren aprobación y contenido excluido. C.4 no implementa `AUTO_SAVE`, ni permite al modelo decidir la categoría final. La clasificación de A es una propuesta no confiable. Una futura autorización autónoma debe depender de validaciones deterministas ejecutadas sobre texto/evidencia exactos, resolución estructural de Self, predicates allowlisted, secret screening, sensibilidad conservadora, deduplicación, conflictos, snapshot vigente y un consentimiento de análisis vigente. Debería limitarse inicialmente a ADD append-only de categorías explícitas; ningún REPLACE automático. Los sensibles seguirían en cola y requerirían confirmación individual.

La frontera B.2b.8b hoy consume una capability de confirmación B.2b.7. No se debe fabricar una capability pasando `auto_save: true`. Una fase posterior tendría que diseñar una autoridad de propósito distinto, one-use y creada exclusivamente por código determinista, enlazada al candidato, fingerprint, snapshot, operación ADD exacta, consentimiento vigente y destinatario, y verificarla dentro de la sección crítica del escritor. Si eso requiere cambios en coordinator/writer, deben diseñarse y auditarse antes de cualquier ejecución. La aprobación persistente de analizar no concede ese permiso.

## Pruebas y límites demostrados

Las pruebas nuevas utilizan directorios temporales, consentimiento sintético, candidatos ficticios y detectores simulados. Cubren consentimiento que sobrevive a recreación del store, versión vieja, revocación, exclusiones persistentes, corruptos, que el consentimiento persistido no activa análisis sin composición de código, análisis solo con flag+detector sintético sobre nuevo stdin, opt-out de mensaje antes del detector, expiración y fecha de vencimiento manipulada, scrub, duplicados, rechazo/descarte, grupos, confirmación individual, confirmación incorrecta, invalidación por exclusión/revocación, concurrencia cooperativa entre instancias y procesos, cola corrupta y ausencia de escritura. Las pruebas C.2 existentes comprueban que el resultado de una tool no se pasa al detector; no pueden demostrar la procedencia de una paráfrasis posterior del usuario. En la validación final: 120 pruebas de Automatic Memory/contexto, 327 pruebas Memory/Automatic Memory y 520 pruebas de la suite completa; todas pasaron sin fallos ni omisiones.

No validan calidad de modelo, privacidad semántica exhaustiva, identidad humana, ACL de Windows, resistencia a malware del mismo usuario, terminación abrupta del proceso en cada punto de rename, durabilidad eléctrica, escritor externo sin lock, integración de propuestas desde la API real, ni persistencia en memoria. La CLI solo ofrece procedencia para el turno directo actual: no puede saber si una reformulación de ese turno repite un resultado de CRM, facturación, pacientes, correo, calendario o banco. El comportamiento actual no evalúa resultados de tools; la paráfrasis podría parecer texto directo a una futura integración. Antes de conectar un extractor real, C.5 debe diseñar y probar una marca de procedencia/taint que impida aprender esos resultados y sus reformulaciones, o excluir esas clases de conversaciones completas. Los regex no resuelven esto. No se hizo ninguna llamada real a OpenAI ni escritura a Memory1/Memory2.

## Condiciones para C.5 y llamadas reales

🔴 DECISIÓN TUYA NECESARIA — No hacer llamadas reales hasta que la configuración efectiva de retención se verifique para la cuenta/proyecto/endpoint concretos y aceptes expresamente sus condiciones. No se verificó esa configuración en esta auditoría y no se accedió a credenciales.

Antes de conectar el extractor, C.5 debe: (1) respetar el opt-out de mensaje implementado; (2) conservar procedencia de resultados de tools y de contenido derivado, sin convertir reformulaciones del usuario en recuerdos automáticos; (3) cubrir CRM, facturación, pacientes, correo, calendario, bancos y otras fuentes operativas, con los sistemas originales como fuente de verdad; (4) convertir las categorías de bajo riesgo confirmadas en reglas/predicates deterministas revisables; y (5) mantener el consentimiento local separado de cualquier permiso de escritura. La revocación global entre dispositivos queda diferida hasta que exista una arquitectura de identidad y sincronización aprobada. Memory2 seguirá apagada por defecto después de una migración; activar recuperación o escritura requerirá autorización explícita separada.
